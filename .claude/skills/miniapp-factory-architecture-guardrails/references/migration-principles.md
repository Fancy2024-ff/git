# 迁移原则：现状结构 → 最终版目标结构

> 本 Skill 约束的是**目标结构**；当前仓库是**现状结构**，两者有差距。本文件定义如何在不停摆、
> 不硬重构整仓库的前提下，让项目持续朝目标结构收敛。

## 基本立场

1. **当前项目是「现状结构」**：业务集中在 `core/pipeline/runner.py`、`apps/api/main.py`，
   能力/分类已部分抽出（`core/capabilities`、`core/agents/classification`），但 worker/runtime/
   platforms/persistence/domain/integrations 等目标目录多数尚未实体化。
2. **Skill 约束的是「最终版目标结构」**：见 `target-architecture.md`。
3. **不要求一次性全迁移**：禁止借「对齐架构」之名发起大规模重写，那会引入大批回归。
4. **新增代码必须优先朝目标结构靠拢**：旧的可以缓，新的不能歪。

## 何时允许老代码暂存

- 改动只是维护现有 step / 现有路由的既有行为，未引入新业务领域。
- 目标目录尚未建立，且本次新增逻辑**很小**、可独立封装、日后易整体搬迁。
  → 暂存现状位置，但在改动说明标记技术债（注明应落的目标层）。

## 何时必须顺手抽离（不允许继续暂存）

- 新增的是一个**新业务领域**（新能力、新平台、新后台任务、新 provider）。
- 新逻辑若留在原处会与旧代码缠绕、日后难以拆分。
- 出现 placement-rules 的「绝对不允许」项（平台 if-else 进 pipeline、能力散落、写死等）。
  → 必须建立/使用对应 core 层目录，把新逻辑落对位置，哪怕多花点时间。

## 何时先记技术债、而不是硬重构

- 想动的是**已存在的大文件历史逻辑**（如 runner.py 既有步骤），且本次需求不要求改它。
  → 不要顺手大改；记一条技术债（「runner.py 编排与业务未分离，待 pipeline 重构」），
    本次只保证**新增**部分不加剧问题。
- 重构范围会触及构建/QA/产物/API 等稳定链路。
  → 先记债、分阶段，不在一个改动里同时重构 + 加功能。

## 收敛节奏

每次新增功能 = 一次小的向目标结构靠拢的机会：
新逻辑落对层 + 必要时把它紧邻的一小块旧逻辑顺势抽离（仅限低风险、与本次强相关的部分）。
积少成多，而非一次性大迁移。

## 技术债标记格式（写在 PR/改动说明里）

```
技术债：<这段逻辑> 目标应落在 core/<层>/，因 <目标目录未建 / 避免触及稳定链路> 暂存于 <现位置>。
后续动作：<建目录后整体迁移 / 随下次相关需求抽离>。
```
