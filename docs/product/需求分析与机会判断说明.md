# 需求分析与机会判断：三个评分讲清楚

> 这份文档回答两个问题：**需求分析是怎么做的？** 和 **凭什么觉得一个 App 是机会？**
> 系统里有三个评分先后接力完成判断，本文把它们的分工、公式、数据流、产物一次讲透。
> 所有公式均与代码一致（`core/pipeline/runner.py` + `core/agents/research/`），可逐项核对。

---

## 一、先建立正确的心智模型：不是"三套评分打架"，是"一条链上三问"

需求分析在流水线上是**连续的三个步骤**，越往后判断越深。把它想成漏斗，不是三个并列的分。

```
候选 App
  │
  │  步骤2  DemandAnalysisAgent         问：用户到底要不要这东西？
  │         → 需求强度分 demand_score (0-100)         产物 analysis.json
  │
  │  步骤3  GapCheckAgent               问：小程序平台上有没有同类？
  │         → 平台缺口分 gap_score (0-100)            产物 gap-check.json
  │
  │  步骤4  OpportunityScoreAgent       问：综合看值不值得做？
  │         → 机会综合分 opportunity_score (0-100)    产物 opportunity-report.json
  │         （把前两步的分当原料，5 维加权）
  │
  │  步骤4.5 ProductDecisionAgent       问：能不能真做成可上架的小程序？
  │         → 双总分 + 最终建议                       产物 execution-decision.json 等
  │         （把前面结果再加落地性/合规/品牌，给"做/拆/缓/弃"）
  ▼
最终建议：immediate_execute / split_then_execute / research_only / reject
```

一句话记忆：**先问需求真不真（步骤2），再问平台缺不缺（步骤3），再问综合值不值（步骤4），最后问能不能真落地（步骤4.5）。**

> 重要诚实声明：以上**主链路是规则驱动**（写死的可解释公式，`USE_LLM=false` 也能完整跑出结果），
> **不是 LLM 在打分**。项目另有一套 LLM 增强（`core/agents/research/demand_llm.py`，需 `USE_LLM=true` + API key），
> 默认不启用，目前只补充文字解释、不重算分数。

## 二、为什么"在 App Store / Google Play 火"能当机会信号？

这是整个判断的底层逻辑，先说清楚再讲分数：

> **机会 = 需求已被验证 + 小程序平台还没有。**

- **需求已被验证**：一个 App 在 App Store / Google Play 有高下载、高评分，说明真实有人用、愿意用；
  而且它能上架，意味着大概率已通过苹果/谷歌的合规审核——我们不赌没验证过的需求。
- **小程序平台空白**：如果微信/支付宝/抖音小程序里还没有同类产品，就是"需求已证实、供给缺位"的搬运窗口。

所以我们**不发明需求**，只找"海外已验证、但国内小程序端缺位"的产品，把它裁剪成小程序。
但——**热门 ≠ 适合直接做小程序**（见第六节 Canva 案例），这正是步骤4.5 要兜住的。

## 三、步骤2：需求强度分（demand_score）

**做什么**：评估"这个 App 的需求有多强"。
**实现**：`core/pipeline/runner.py:demand_analysis_agent`（约 L264）。
**满分 100，6 个可解释维度相加**：

| 维度 | 分值范围 | 规则 |
|---|---|---|
| 下载量 | 0–30 | >500万=30；>200万=25；>50万=18；>10万=12；其它=5 |
| 评分 | 0–20 | `rating × 4.2`，上限 20 |
| 评论数 | 0–15 | >1万=15；>3千=12；>500=8；其它=4 |
| 变现模式 | 0–15 | 订阅/freemium=15；买断=12；其它=5 |
| 功能丰富度 | 0–10 | `功能数 × 2`，上限 10 |
| 更新频率 | 10 | 本地拿不到真实数据，给默认 10（**诚实：这一项是占位**） |

**结论阈值**：demand_score ≥ 60 → "需求已被市场验证"，否则"需求待进一步验证"。
**额外产出**（不只是分数）：`target_users`（目标用户）、`pain_point`（痛点）、`market_validation`（市场验证依据）。

---

## 四、步骤3：平台缺口分（gap_score）

**做什么**：检查目标小程序平台上"有没有同类产品"，缺得越多机会越大。
**实现**：`core/pipeline/runner.py:gap_check_agent`（约 L320），平台清单来自平台注册表。
**逻辑**：
- 对每个 active 平台判断"覆盖程度"`coverage_level`（strong/weak/missing）和"产品是否适配该平台"`product_fit`。
- 某平台 `missing` 或 `weak` 且适配 → 计入"缺失平台"。
- **gap_score = 缺失平台数 / active 平台总数 × 100**。
- `opportunity_level`：缺 ≥4 个=高；≥2 个=中；否则低。

> 说明：当前覆盖判断是**本地启发式规则**（如按下载量推断微信是否已被覆盖），
> 注释里标了"待接入真实搜索"——这是诚实的已知简化，不是真去各平台搜了一遍。

## 五、步骤4：机会综合分（opportunity_score）

**做什么**：把前面的信号 + 落地相关因素，加权成一个综合机会分。
**实现**：`core/pipeline/runner.py:opportunity_score_agent`（约 L405）。
**5 个维度加权**：

| 维度 | 权重 | 来源/算法 |
|---|---|---|
| 需求强度 demand | 25% | 来自步骤2 的 demand_score |
| 小程序缺口 gap | 25% | 来自步骤3 的 gap_score |
| 小程序适配度 fit | 20% | 轻工具/短流程/适合分享/不依赖复杂原生能力，4 项各 +25 |
| 实现难度 impl | 15% | 高分=容易；页面越多/需支付/含复杂能力 → 扣分 |
| 风险 risk | 15% | 默认 85；命中 health/finance/gambling 等敏感词降到 45–50 |

公式（代码 L445）：
```
opportunity_score = demand×0.25 + gap×0.25 + fit×0.20 + impl×0.15 + risk×0.15
```
**推荐阈值**：≥70 立即执行 / 50–70 值得尝试 / <50 暂缓。
（注：复杂能力判断用关键词 `camera/ar/video/3d/hardware`，命中则 fit、impl 双降。）

## 六、步骤4.5：产品决策框架（双总分 + 最终建议）

这是最新一轮升级的核心，也是解决"热门≠能直接做"的关键层。
**实现**：`core/agents/research/`（framework / decision / product_research / artifacts）。

### 6.1 为什么要再加一层？

前面三步都在回答"**值不值得做**"（市场角度）。但一个 App 市场机会再高，
也可能**根本做不成可用的小程序**（比如要复杂画布编辑、或我们没有对应能力 provider）。
所以这一层把判断拆成**两个独立总分**，避免"高人气 = 直接上架"的误判。

### 6.2 双总分（这是你汇报要重点讲的）

| 总分 | 含义 | 公式（与代码一致） |
|---|---|---|
| **market_opportunity_score** | 市场机会有多大 | `demand_score×0.6 + gap_score×0.4` |
| **miniapp_feasibility_score** | 能不能真做成小程序 | `miniapp_fit×0.6 + 能力齐备(+20) + 单任务(+10) − 空壳风险(−20)` |

外加三个辅助分：`brand_risk_score`（品牌/商标风险，高=差）、`review_risk_score`（审核风险）、`execution_confidence`（置信度 0–1）。

### 6.3 决策门槛（`decision.py`，HIGH=70 / MID=50）

| 条件 | 建议 |
|---|---|
| market & feasibility 都 ≥70，且无高风险 | **immediate_execute**（立即执行） |
| market 高、feasibility 中（≥50 但不够高） | **split_then_execute**（拆分后执行） |
| feasibility < 50 但可拆 | **split_then_execute** |
| feasibility < 50 且不可拆 | **research_only**（仅调研） |
| market < 50 | **reject** 或 research_only |
| 品牌或审核风险 ≥70 | **一律禁止 immediate_execute**（强制降级） |

**铁律**：feasibility < 50 → 绝不 immediate_execute；高风险 → 绝不 immediate_execute。

### 6.4 功能拆解 + MVP 裁剪（mvp-split-plan.json）

决策框架还会把原产品拆开：
- `replicable_features`：能搬到小程序的功能
- `non_replicable_features`：搬不了的（如多图层/时间轴）
- `substitution_strategies`：搬不了的怎么用替代方案
- `recommended_mvp`：建议做成什么垂直小程序（名称/app_type/能力/首版范围）

## 七、案例：Canva 为什么不是"立即执行"

这是最能体现框架价值的例子（实跑结果）：

| 指标 | 值 | 说明 |
|---|---|---|
| market_opportunity_score | ≈94 | 全球 5000万下载，市场机会极高 |
| miniapp_feasibility_score | ≈0 | 依赖复杂画布/图层/时间轴 + 缺图像 provider |
| brand_risk_score | 80 | 含 "canva" 知名品牌词，直接命名有商标风险 |
| **recommendation** | **split_then_execute** | 不是 immediate_execute |
| recommended_mvp | "证件照/一键抠图（垂直 MVP）" | 砍掉复杂编辑，只做高频单点 |

**讲解话术**："Canva 市场分 94 很高，但小程序落地性 0——它要复杂画布编辑，小程序做不了，还有品牌风险。
所以系统判它'拆分执行'：不照搬 Canva，只做'证件照/抠图'这种能在小程序闭环的垂直单点。这就是'热门≠适合直接小程序化'。"

## 八、产物文件清单（在哪看）

全部在 `data/outputs/{jobId}/`：

| 文件 | 来自步骤 | 内容 |
|---|---|---|
| analysis.json | 步骤2 | 需求强度分 + 6 维拆分 + 痛点/目标用户（**兼容旧版，前端仍读**） |
| gap-check.json | 步骤3 | 平台缺口分 + 缺失平台清单 |
| opportunity-report.json | 步骤4 | 机会综合分 + 5 维 + 推荐动作 |
| demand-analysis.json | 步骤4.5 | 市场需求/用户/场景/竞品 + market_opportunity_score |
| miniapp-feasibility-report.json | 步骤4.5 | 适配/能力依赖/生成可行性/审核风险 + miniapp_feasibility_score |
| mvp-split-plan.json | 步骤4.5 | 拆分方案 + 推荐 MVP |
| **execution-decision.json** | 步骤4.5 | **双总分 + 最终建议 + 阻塞项 + 下一步（汇报核心）** |
| demand-analysis.md | 步骤4.5 | 给老板/产品看的人话摘要（**演示就打开这个**） |

> 三个"分"名字相近但**含义不同、不冲突**：
> - `demand_score`（步骤2）= 纯需求强度
> - `opportunity_score`（步骤4）= 5 维综合机会
> - `market_opportunity_score` / `miniapp_feasibility_score`（步骤4.5）= 决策用的双总分
> 汇报时**重点讲步骤4.5 的双总分和最终建议**，前面三步一句话带过（"底层有需求分、缺口分、机会分逐层支撑"）。

## 九、当前诚实的局限（被追问时主动说）

- 主链路是**规则驱动**，不是 LLM 实时分析；LLM 增强默认未启用。
- 平台缺口判断是**本地启发式**，未真去各平台搜索（注释已标）。
- 更新频率维度是**占位默认值**（本地拿不到真实更新数据）。
- `recommended_mvp` / 替代方案是**规则模板化产出**，未做深度领域定制。
- 这些都不影响判断闭环可用，但要诚实说清，别包装成"全 AI 智能分析"。
